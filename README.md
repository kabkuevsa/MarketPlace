# Marketplace — микросервисный маркетплейс

Учебный проект: **«Маркетплейс с заказами на событиях» (тема 3)**.

Marketplace — веб-приложение маркетплейса, построенное на микросервисной архитектуре. Пользователь может зарегистрироваться, войти в систему, просматривать каталог товаров, управлять корзиной, оформлять заказы и отслеживать доставку.

Оформление заказа координируется сервисом Orders с использованием паттерна **Saga**. Для асинхронного обмена событиями используется RabbitMQ: после успешного завершения заказа событие `OrderCompletedEvent` независимо обрабатывается сервисами Warehouse и Delivery.

## Возможности

- Регистрация и вход пользователей.
- Аутентификация с использованием JWT.
- Каталог товаров и категории.
- Добавление товаров в корзину, изменение количества и удаление товаров.
- Оформление заказов с указанием адреса доставки.
- История заказов.
- Резервирование и подтверждение товарных остатков.
- Имитация обработки платежей.
- Координация оформления заказа с помощью Saga и компенсирующих действий.
- Асинхронное создание доставки после успешного завершения заказа.
- Управление статусами доставки.
- Единая точка входа к API через API Gateway.
- Автоматизированные тесты и сборка в GitHub Actions.
- Запуск полного приложения с помощью Docker Compose.

## Архитектура и состав системы

В решении находятся шесть бизнес-микросервисов, API Gateway и Web-приложение.

| Компонент | Назначение | База данных |
|---|---|---|
| Identity | Регистрация, аутентификация, пользователи, роли и JWT | `identity_db` |
| Catalog | Товары, категории и корзина | `catalog_db` |
| Orders | Заказы и оркестрация Saga | `orders_db` |
| Warehouse | Остатки товаров и резервы | `warehouse_db` |
| Payments | Имитация обработки платежей | `payments_db` |
| Delivery | Создание доставки и управление её статусом | `delivery_db` |
| Gateway | Маршрутизация запросов и проверка JWT | Не используется |
| Web | Пользовательский интерфейс на Blazor Server | Не используется |

Каждый бизнес-микросервис владеет собственной базой данных. Сервисы не обращаются напрямую к таблицам друг друга. Для синхронных операций используется HTTP, для асинхронных событий — RabbitMQ.

Подробная схема и описание взаимодействий приведены в [документе об архитектуре](docs/ARCHITECTURE.md).

## Запуск приложения через Docker Compose

### 1. Клонирование репозитория

```bash
git clone https://github.com/kabkuevsa/MarketPlace.git
cd MarketPlace
```

### 2. (Необязательно) Задание локальных переменных окружения

В Compose предусмотрены значения по умолчанию для локальной демонстрации. При необходимости их можно переопределить.

Для Windows CMD:

```cmd
set MARKETPLACE_JWT_SECRET=replace-with-a-long-local-development-secret
set RABBITMQ_PASSWORD=replace-with-a-local-password
```

Переменная `MARKETPLACE_JWT_SECRET` должна содержать достаточно длинный секретный ключ. Не используйте демонстрационные значения в production-среде и не помещайте реальные секреты в Git.

### 3. Проверка конфигурации Compose

```bash
docker compose -f docker/docker-compose.yml config -q
```

### 4. Сборка и запуск всех контейнеров

```bash
docker compose -f docker/docker-compose.yml up --build -d
```

### 5. Проверка состояния контейнеров

```bash
docker compose -f docker/docker-compose.yml ps
```

В конфигурации описано 15 контейнеров:

- 6 контейнеров PostgreSQL;
- 1 контейнер RabbitMQ;
- 6 бизнес-микросервисов;
- 1 API Gateway;
- 1 Web-приложение.

### 6. Открытие приложения

Web-приложение:

<http://localhost:5196>

Проверка состояния Gateway:

<http://localhost:5002/health>

Панель управления RabbitMQ:

<http://localhost:15672>

Локальные учётные данные RabbitMQ по умолчанию:

- Логин: `marketplace`
- Пароль: `marketplace_dev_password`

Пароль можно переопределить переменной `RABBITMQ_PASSWORD`.

### 7. Остановка приложения

```bash
docker compose -f docker/docker-compose.yml down
```

Именованные тома сохраняются, поэтому данные PostgreSQL остаются после остановки контейнеров.

Чтобы удалить контейнеры и все тома с данными:

```bash
docker compose -f docker/docker-compose.yml down -v
```

**Внимание:** параметр `-v` удаляет постоянные данные баз данных.

## Как обрабатывается заказ

1. Orders получает информацию о товарах и ценах от Catalog.
2. Orders создаёт заказ.
3. Orders запрашивает резервирование товара у Warehouse.
4. Orders обращается к Payments для имитации оплаты.
5. При успешной оплате заказ получает статус `Completed`.
6. Orders публикует событие `OrderCompletedEvent` в RabbitMQ.
7. Warehouse получает собственную копию события и подтверждает резерв.
8. Delivery получает собственную копию события и создаёт запись о доставке.

Если один из этапов Saga завершается ошибкой, Orders выполняет предусмотренные компенсирующие действия, например освобождает резерв товара или меняет статус заказа.

Создание доставки выполняется асинхронно. Поэтому сразу после завершения заказа Web-интерфейс может кратковременно показывать, что доставка ещё создаётся.

## Очереди RabbitMQ

Событие `OrderCompletedEvent` обрабатывается двумя независимыми очередями:

- `warehouse-order-completed` — для Consumer сервиса Warehouse;
- `delivery-order-completed` — для Consumer сервиса Delivery.

Так каждый сервис получает собственную копию события и обрабатывает её независимо от другого сервиса.

## Автоматизированные тесты

Тестовый проект расположен в `tests/Marketplace.Tests`.

Текущий набор включает 26 тестовых случаев:

| Область | Количество |
|---|---:|
| Бизнес-логика Delivery | 21 |
| Интеграционные тесты Consumer Warehouse | 5 |
| **Всего** | **26** |

Тесты Delivery проверяют создание доставки, валидацию входных данных и переходы статусов. Тесты Warehouse вызывают реальный Consumer и используют отдельную базу PostgreSQL; контекст сообщения MassTransit подменяется тестовым объектом.

### Подготовка тестовой базы

Запустите PostgreSQL Warehouse:

```cmd
docker compose -f docker\docker-compose.yml up -d postgres-warehouse
```

Создайте отдельную тестовую базу (один раз):

```cmd
docker compose -f docker\docker-compose.yml exec postgres-warehouse createdb -U postgres warehouse_test_db
```

Если база уже существует, повторно создавать её не нужно.

Задайте строку подключения в Windows CMD:

```cmd
set "WAREHOUSE_TEST_CONNECTION_STRING=Host=localhost;Port=5445;Database=warehouse_test_db;Username=postgres;Password=postgres"
```

Запустите тесты:

```cmd
dotnet test Marketplace.slnx --configuration Release
```

Последняя подтверждённая локальная проверка: **26 успешно выполненных тестов, 0 ошибок**.

### Непрерывная интеграция (CI)

Workflow находится в `.github/workflows/ci.yml`.

GitHub Actions:

1. Получает исходный код репозитория.
2. Устанавливает .NET 10 SDK.
3. Запускает PostgreSQL для интеграционных тестов.
4. Восстанавливает NuGet-зависимости.
5. Собирает решение в конфигурации Release.
6. Запускает автоматизированные тесты.

## Ограничения проекта

- Платёжная система имитируется; внешний платёжный провайдер не подключён.
- Транзакционный паттерн Outbox не реализован.
- Обработка сообщений RabbitMQ асинхронная, поэтому доставка может появиться в интерфейсе с небольшой задержкой после завершения заказа.
- Учётные данные Docker Compose предназначены для локальной разработки и демонстрации, а не для production-развёртывания.
